> **حالة الوثيقة:** مواصفات سلوك ومعمارية مستهدفة، وليست وصفًا لما هو منفّذ. القسم 3 يحدد بدقة ما يعمل اليوم في luma3 وما لم يُبنَ بعد.
> **المرجع للتنفيذ الحالي:** [AI_AND_MARKETING.md](AI_AND_MARKETING.md). **قرارات المنتج:** [DECISIONS_2026-11.md](DECISIONS_2026-11.md).

## 1. التعريف المعتمد

**لووم للتسويق محرك مستقل لتحليل الأعمال واكتشاف الفرص والتخطيط التسويقي.**

- **ماذا يفهم:** تشغيل المنشأة ومواردها واقتصادياتها وأهدافها.
- **بماذا يربطها:** السوق والتوقيت.
- **ماذا يقدّم:** مقترحات وخططًا مدعومة بالأدلة، قابلة للدراسة والتنفيذ والقياس.
- **كيف يتحسن:** من معرفة المنشأة ونتائج مبادراتها، ثم من نماذج متخصصة عندما تتوفر البيانات المناسبة.
- **أين يعمل:** داخل لوما أولًا، بمعمارية تسمح بربطه بأنظمة وقطاعات أخرى.
- **كيف يُستخدم:** بدون محادثة. المستخدم يجد تحليلًا وفرصًا وخططًا ونتائج، ويتخذ قرارات عليها.

### 1.1 مبادئ غير قابلة للتفاوض

| # | المبدأ | ماذا يعني تقنيًا |
|---|---|---|
| P1 | **الداخل أولًا** | لا تُقترح حملة بسبب مناسبة أو ترند وحده. الحدث الخارجي يحدد التوقيت والرسالة فقط، ويجب أن يرتبط بفرصة داخلية (طاقة متاحة، طلب غير مخدوم، عملاء متأخرون…). |
| P2 | **الأرقام بالكود، والصياغة بالنموذج** | كل مقياس وحساب جدوى وفحص طاقة يُنفَّذ بكود مُختبر. النموذج اللغوي يفسّر ويصوغ ولا يحسب ولا يختار نطاق البيانات. |
| P3 | **لا اختلاق** | البيانات الناقصة تُعلن. عند غياب وصفة استهلاك لا يُقدَّر عدد الخدمات التي يكفيها المخزون، وعند غياب التكاليف لا تُعلن ربحية. وعند تعطل AI أو مصادر الترند يُقال ذلك صراحة. |
| P4 | **ثلاث درجات للمعلومة** | كل معلومة تُوسم بأنها **مرصودة** (من مصدر) أو **مستنتجة** (من قاعدة أو نموذج) أو **افتراض يحتاج اختبارًا**، ويظهر الوسم للمستخدم. |
| P5 | **الاقتراح ليس تنفيذًا** | الربط التحليلي للقراءة فقط. إرسال حملة أو تغيير سعر أو فتح موعد يمر بصلاحية ومسار اعتماد منفصل، ولا يحدث تلقائيًا. |
| P6 | **الهدف ليس وعدًا** | الفصل بين «هدف مقترح» و«توقع من نموذج» و«نتيجة مرصودة»، وبين «الإيراد المنسوب» و«الإيراد الإضافي». |
| P7 | **العزل** | بيانات كل منشأة معزولة في التخزين والاسترجاع والذاكرة والكاش والتدريب. |

## 2. الأسئلة التي يجيب عنها المنتج، وأين تُجاب

| السؤال | المكوّن المسؤول | المخرج |
|---|---|---|
| أين توجد فرصة فعلية؟ | محرك الفرص (§6.5) | بطاقات الفرص |
| ما الذي يستحق الترويج؟ | المقاييس + كاشفات الخدمة (§6.4، §6.5) | فرص `offering_promotion` و`cross_sell` |
| هل نستوعب الطلب المتوقع؟ | فاحص الطاقة والمخزون (§6.6) | `capacity_check` و`inventory_check` |
| هل العرض مجدٍ؟ | حاسبة الهامش ونقطة التعادل (§7) | `margin_check` مع السيناريوهات |
| من الجمهور؟ متى وأين؟ | الشرائح + الرادار + التقويم (§6.8، §9) | `target_segment` و`channel` و`timing` |
| خصم أم باقة أم قيمة مضافة أم تحسين حجز؟ | منتقي التدخل وكتيبات التسويق (§6.7، §6.10) | `recommended_action` مع البدائل المرفوضة وأسبابها |
| ماذا تعلمنا؟ | ذاكرة النتائج (§10) | صفحة النتائج + سجل القرارات |
| ما المناسب للفترة القادمة؟ | المخطِّط (§6.9) | الخطة الشهرية والأسبوعية |

## 3. الوضع الحالي في luma3: ما هو موجود وما ينقص

لووم ليس بداية من الصفر. يوجد في `src/server/domains/marketing/*` و`analytics/*` أساس قوي، لكنه **مضمّن داخل لوما ويقرأ جداولها مباشرة**، وبعض محاور المواصفات غير موجودة.

| المحور في المواصفات | الموجود اليوم (مُختبر) | الناقص |
|---|---|---|
| لقطة بيانات ومقاييس (§3، §5ج) | `buildSnapshot`: لقطة مخزّنة في `metric_snapshots` بـ hash و`data_as_of` وقياس كفاية (`none`/`low`/`ok`). تشمل طلب كل خدمة (مشاهدات، بدء حجز، لا مواعيد، انتظار، مكتمل، ملغى) ورضاها ودورة زيارتها وهامشها والطاقة المجدولة وأزواج الخدمات والعملاء المتأخرين. | **سجل تعريفات للمقاييس** (`metric_definitions`) بإصدارات. مقاييس على مستوى الحقل (قيمة لكل مقياس وبُعد). المقاييس المالية الجديدة غير مضمّنة: الرواتب والعمولات وعمولة السوق ورسوم الدفع ومصدر العميلة ونتائج الجرد. |
| ملف معرفة المنشأة (§3 من المواصفات) | `marketing_preferences`: الميزانية وسقف الخصم والقنوات وجدولة الخطط، و`prior_decisions` داخل اللقطة. | **ملف معرفة كامل** بحقائق موسومة المصدر والتاريخ والدرجة (محسوب / صريح / مستنتج)، والأهداف والأولويات، والخدمات المراد تنميتها أو المستبعدة، ونبرة المحتوى، وأسباب قبول أو رفض المقترحات. |
| المنتج / المادة / المورد / الوقت (§4) | `service_material_recipes` (وصفة مواد لكل خدمة) و`inventory_items` و`stock_counts`، والموارد (غرف وكراسي) كخاصية، وجداول الطاقم. | **نموذج موحّد** يميّز: منتج للبيع / مادة تشغيل / كلاهما / مورد / مهارة ووقت. **ربط الخدمة بكل متطلباتها** داخل فاحص واحد. اليوم `capacity_check` و`margin_check` في التوصيات قيمتهما الافتراضية `unknown`. |
| الموصلات والتوحيد (§5أ، §5ب) | لا يوجد. لووم يقرأ جداول لوما مباشرة. | طبقة **Connector** بعقد بيانات قانوني (canonical) و**Normalization** ومزامنة وتتبع حالة الاتصال. |
| محرك الفرص (§5د، §6) | `rules.ts`: 12 كاشفًا قابلًا للتفسير (فترات هادئة، استعادة، إبراز خدمة، مراجعة سعر أو تكلفة، طلب يفوق المتاح، تكاليف مفقودة، باقات من الأزواج، ولاء بدل الخصم، تسهيل الحجز، لا مواعيد، موسم من التقويم المعتمد، تحسين العرض، مراجعة آخر حملة)، مع `fingerprint` لدمج المكرر. | **دورة الفرصة بمراحلها العشر**، وفحوص الطاقة والمخزون والهامش الفعلية، و**ترتيب بأوزان قابلة للضبط مع تفسير**، و**جدول أدلة** منفصل، وإدارة التعارض بين المبادرات. |
| التسعير والخصومات (§8) | `pricing`: مراجعة سعر أو تكلفة، و**مقترح سعر** لا يُنشأ إلا بنقرة المالكة ولا يُطبّق إلا باعتمادها. سقف الخصم يُفحص في `validate.ts`. | **حاسبة نقطة التعادل** (الزيادة المطلوبة لتعويض الخصم مع تكلفة الحملة)، ومقارنة البدائل (باقة أو قيمة مضافة)، وتقدير وصول الخصم لمن كان سيشتري أصلًا. |
| الخطط (§9) | خطة شهرية وأسبوعية بإصدارات غير قابلة للتعديل (`plan_versions`)، وانتقالات حالة (اقتراح، مراجعة، اعتماد، بدء، إكمال، تأجيل، رفض)، وتعليقات، ومقارنة بين الإصدارات، وتصدير. خطة بالقواعد عند غياب AI. | متطلبات تشغيلية مرتبطة بالطاقة لكل نشاط، ومسؤوليات، ومؤشرات نجاح بخط أساس محسوب. |
| المخطِّط بالنموذج اللغوي (§5و، §12) | `runAi` بمخرجات JSON Schema صارمة، وسجل `prompt_versions`، وكاش معزول لكل منشأة، وسجل `ai_runs` (إلحاق فقط، مع التكلفة)، وميزانية شهرية ذرية، وسقوط إلى القواعد. | أدوات قراءة مقيّدة بدل حقن كامل اللقطة، وإدخال المعرفة التسويقية المسترجعة، وتوزيع المهام بين نماذج بأحجام مختلفة. |
| المراجعة والتحقق (§5ز) | `validate.ts`: الاستشهادات يجب أن تكون مفاتيح في اللقطة، والأرقام المقيسة تطابق اللقطة، والأرقام غير المسنودة تُوسم أو تُرفض، والتوقعات غير المسنودة تُحذف، وفحص سقف الخصم وعدم ترويج المواعيد الممتلئة، وتواريخ المواسم من التقويم المعتمد فقط. | فحص الميزانية الإجمالية للخطة، وفحص المخزون، وفحص التفضيلات (لا خصومات، خدمات مستبعدة). |
| رادار الترندات (§14) | مصادر RSS وروابط المستخدم، وجلب آمن من SSRF، وإزالة التكرار، وقوة الدليل (`anecdotal` / `early_signal` / `quantified`)، والحداثة، والقِدم، والإضافة لخطة أسبوعية. التقويم الموسمي **يعتمده المالك**. | **التقييم بالقواعد فقط** (لا يستخدم النموذج). لا مصادر API ولا مصادر رسمية للمناسبات. الفصل بين التوعوي والترويجي في المناسبات الصحية غير مطبق آليًا. |
| الحملات والقياس (§16، §17) | الموافقة والقنوات والرضا وقائمة الحظر والحد من التكرار وساعات الهدوء ومجموعة مقارنة (holdout)، والفصل بين **المنسوب** و**الإضافي** بحد أدنى للعينة (30 لكل مجموعة)، ونافذة نسب معلنة. | ربط **الفرصة ← القرار ← التنفيذ ← النتيجة** في سجل واحد، وكيان التجارب بأنواعه، وجودة القياس، والعوامل الخارجية. |
| الذاكرة والتعلم (§15، §16) | `fingerprint` يمنع تكرار التوصية، وقرارات قبول أو رفض أو تأجيل. | **سلّم مراحل القرار** (إعجاب، اعتماد، تنفيذ، اكتمال، نتيجة) مع **تصنيف أسباب الرفض**، وسجل نماذج متعلّمة، وتقييم زمني، وبوابات ترقية ورجوع. |
| المعرفة التسويقية (§13) | تعليمات النظام في `prompts.ts` فقط. | **مكتبة كتيبات منظمة** بمصدر وتاريخ ونطاق قطاعي، مع استرجاع مفلتر. |
| القطاعات (§19) | الصالونات والخبيرات فقط (`business_type`). | **حزم قطاعية** تعرّف معنى الطاقة والمقاييس والفرص المناسبة لكل قطاع. |
| الجدولة (§21) | `marketing.scheduler` كل ساعة حسب وقت المنشأة المحلي، و`ai_jobs` بحالات ومحاولات محدودة، وحماية من التكرار لكل (منشأة، نوع، فترة). | **إعادة التحليل عند تغير جوهري** (نفاد مخزون، امتلاء مواعيد، غياب موظفة، نتيجة حملة)، مع تجميع التغيرات. |
| الواجهة (§11) | صفحة `/app/{slug}/marketing` بلا شات، فيها الخطط والتوصيات والرادار والحملات. | صفحة رئيسية بملخص الوضع وما ينتظر القرار والنتائج، وبطاقة فرصة كاملة الحقول، وتعديل الأهداف والقيود من الواجهة. |

**الخلاصة:** الأساس الحالي يحقق P2 وP3 وP5 وP6 وP7 جزئيًا. المطلوب ليس إعادة كتابة، بل **استخراج نواة مستقلة** وإضافة ست قدرات ناقصة:

1. العقود القانونية والموصلات.
2. ملف المعرفة.
3. الفحوص الاقتصادية والتشغيلية الحقيقية.
4. الترتيب المفسَّر.
5. ذاكرة القرار والنتيجة.
6. المعرفة التسويقية والحزم القطاعية.

## 4. القرار المعماري: نواة مستقلة على مراحل، وليست خدمة منفصلة من اليوم الأول

### 4.1 الخيار المعتمد

نبني **Loom Marketing Core** كوحدة مستقلة **داخل نفس المستودع** في المرحلة الأولى (`src/loom/`)، بحدود صارمة:

```
┌─────────────────────────────── luma3 (Next.js) ────────────────────────────────┐
│  واجهة لوما: /app/{slug}/marketing  ──►  Loom API (v1)  ◄── أنظمة أخرى لاحقًا   │
│                                             │                                    │
│  ┌──────────────── Loom Marketing Core (src/loom, schema "loom") ─────────────┐ │
│  │ connectors/ ─► normalize/ ─► metrics/ ─► quality/ ─► opportunities/         │ │
│  │      ▲                          │            │             │                │ │
│  │      │                     knowledge/   checks/(capacity, inventory, margin)│ │
│  │  LUMA connector                 │            │             │                │ │
│  │  (in-process,                planner/(LLM) ─► validator/ ─► ranking/        │ │
│  │   read-only views)              │                              │            │ │
│  │                              plans/ ◄─ memory/(decisions, outcomes) ◄───────┘ │
│  │                              radar/(signals, calendar)   jobs/(queue)        │ │
│  └─────────────────────────────────────────────────────────────────────────────┘ │
│  جداول لوما التشغيلية (public schema): حجوزات، مالية، مخزون، طاقم…               │
└──────────────────────────────────────────────────────────────────────────────────┘
```

**قواعد الحدود (تُفرض باختبارات وقواعد lint):**

1. كود `src/loom/**` **لا يستورد** من `src/server/domains/**` ولا يقرأ جداول `public` مباشرة. يقرأ فقط عبر **موصل** يُرجع سجلات قانونية.
2. موصل لوما يقرأ عبر **دوال ودروس قراءة مخصصة** (`loom_export.*`) تُرجع بيانات مجمّعة أو مستعارة الهوية، بصلاحيات قراءة فقط ومقيدة بالمنشأة (RLS).
3. لووم يكتب **فقط** في مخطط `loom` الخاص به. الإجراءات التنفيذية (مسودة حملة، مقترح سعر) تُرسل كـ **أوامر** عبر عقد `actions` يملكه النظام المضيف، وتمر بمسار الاعتماد فيه.
4. واجهة لوما تستهلك **Loom API v1** نفسها التي ستستهلكها الأنظمة الخارجية.

### 4.2 لماذا لا نبدأ بخدمة منفصلة

| الاعتبار | خدمة منفصلة الآن | نواة داخلية بحدود صارمة (المعتمد) |
|---|---|---|
| زمن الوصول لقيمة | أبطأ (بنية تحتية، مصادقة بين الخدمات، نشر) | أسرع، وتعيد استخدام المصادقة وRLS والطوابير الحالية |
| الاتساق مع لوما | مزامنة عبر الشبكة، مع تأخر وتكرار | قراءة متسقة داخل نفس المعاملة |
| الاستعداد للاستقلال | فوري | مضمون بالعقود، والاستخراج لاحقًا ميكانيكي: نفس الـ API ونفس المخطط ونفس الموصل عبر HTTP |
| خطر التشابك | منخفض | يُضبط بقاعدة منع الاستيراد واختبار معماري |

**متى نستخرجها كخدمة:** عند ربط أول نظام خارجي غير لوما، أو عندما يتطلب حمل التحليل موارد مستقلة. عندها ينتقل مخطط `loom` لقاعدة منفصلة، ويصبح موصل لوما عميل HTTP لنفس العقد.

## 5. النموذج القانوني (Canonical Model) والعقود

### 5.1 الكيانات العامة

| الكيان | المعنى | حقول أساسية | ملاحظات |
|---|---|---|---|
| `Business` | المنشأة | `sector`, `subsector`, `city`, `region`, `timezone`, `currency`, `locations[]` | `sector` يحدد الحزمة القطاعية |
| `Location` | فرع أو نطاق خدمة | `id`, `city`, `geo?`, `service_area?`, `hours` | |
| `Offering` | ما يُعرض على العميل | `kind`: `service` · `product` · `package` · `membership` · `gift` ، `price`, `status`, `category`, `channel_availability` | معناه الأصلي في المصدر يُحفظ في `source_kind` |
| `OfferingRequirement` | ما تحتاجه الخدمة لتُنفَّذ | `offering_id`, `type`: `material` · `resource` · `skill` · `time`, `ref_id`, `quantity`, `unit`, `confidence`: `recipe` · `estimated` · `unknown` | أساس فحص الطاقة والمخزون |
| `InventoryItem` | صنف مخزون | `usage`: `sellable` · `consumable` · `both`, `on_hand`, `unit`, `unit_cost?`, `reorder_level?` | يمنع معاملة مواد التشغيل كمنتجات للبيع |
| `Resource` | مورد تشغيلي | `kind`: `staff` · `room` · `equipment` · `table` · `vehicle` · `generic`, `skills[]`, `location_id` | المعنى يختلف حسب القطاع |
| `CapacityWindow` | وقت متاح لمورد | `resource_id`, `start`, `end`, `state`: `free` · `booked` · `blocked` · `leave` | من الجداول والإجازات والحجوزات |
| `Customer` | عميل **مستعار الهوية** | `pseudo_id`, `first_seen`, `last_seen`, `visits`, `segments[]`, `acquisition_source`, `consents{}` | لا أسماء ولا أرقام في لووم |
| `Transaction` | عملية بيع أو حجز | `kind`: `booking` · `order` · `membership` · `gift`, `status` (موحّد), `lines[]`, `net`, `tax`, `discount`, `refunded`, `channel`, `occurred_at` | |
| `TransactionLine` | بند | `offering_id`, `resource_ids[]`, `qty`, `net`, `cost_direct?` | |
| `CostFact` | تكلفة | `type`: `material` · `commission` · `payment_fee` · `platform_fee` · `labor` · `overhead`, `amount`, `scope`, `completeness` | الاكتمال إلزامي |
| `DemandSignal` | طلب غير مخدوم أو اهتمام | `type`: `view` · `booking_start` · `no_availability` · `waitlist` · `inquiry`, `offering_id?`, `at` | |
| `Review` | تقييم أو شكوى مؤكدة | `rating`, `offering_id?`, `resource_id?`, `verified`, `at` | الشكاوى المؤكدة فقط |
| `Campaign` / `CampaignExecution` | حملة وتنفيذها | `channel`, `segment`, `cost`, `sent_at`, `holdout` | |
| `Outcome` | نتيجة مبادرة | انظر §10 | |

### 5.2 توحيد الحالات

مثال للحجز (تُحدد قائمة مماثلة للطلب والدفع):

| الحالة القانونية | لوما | نظام آخر (مثال) | تُحسب كبيع؟ |
|---|---|---|---|
| `requested` | `held`, `pending_payment`, `pending_approval` | `tentative` | لا |
| `confirmed` | `confirmed` | `booked` | لا (طلب مؤكد) |
| `fulfilled` | `completed` | `done`, `closed` | نعم |
| `cancelled_customer` | `cancelled` (من العميلة) | `cancelled_by_client` | لا |
| `cancelled_business` | `cancelled` (من النشاط) | `cancelled_by_staff` | لا |
| `no_show` | `no_show` | `missed` | لا |
| `expired` | `expired` | — | لا |

**تعريف الإيراد يُكتب صراحة لكل مصدر** في `source_mappings.revenue_basis`: صافي بعد الخصم وقبل الضريبة وبعد الاسترداد. لا يُفترض.

### 5.3 عقد الموصل (Connector Contract)

```ts
interface LoomConnector {
  readonly kind: 'luma' | 'csv_import' | 'rest' | string;
  describe(): ConnectorManifest;                 // الكيانات المدعومة وحقولها وتعريف الإيراد والمنطقة الزمنية
  healthcheck(conn: ConnectionRef): Promise<ConnectionHealth>;
  // مزامنة تزايدية بمؤشر: تُرجع إنشاء/تحديث/حذف لكل كيان قانوني
  pull(conn: ConnectionRef, entity: CanonicalEntity, cursor: string | null, limit: number): Promise<{
    records: Array<{ op: 'upsert' | 'delete'; source_id: string; source_version: string; data: unknown }>;
    next_cursor: string | null;
  }>;
  // اختياري: أحداث فورية (webhook) تُحوَّل لنفس الشكل
  verifyWebhook?(req: Request): Promise<SourceEvent[]>;
}
```

- **القراءة افتراضية.** الكتابة لا تمر عبر الموصل، بل عبر عقد `ActionPort` منفصل يملكه النظام المضيف (§12.3).
- **الدقة:** `source_version` (أو hash المحتوى) يمنع إعادة المعالجة. الحذف يُطبَّق كإشارة `deleted_at` ولا يُمسح من اللقطات التاريخية.
- **التكرار:** مفتاح فريد `(connection_id, entity, source_id)`. السجلات المشكوك في تكرارها (نفس العميل بمعرّفين) تُجمع في `entity_links` بدرجة يقين، ولا تُدمج تلقائيًا بدرجة منخفضة.
- **موصل لوما الأول** يعمل in-process ويقرأ من دروس `loom_export.*`. يدعم الأحداث الفورية عبر خطافات لوما الحالية (`boot.ts`) دون استدعاء HTTP.

### 5.4 جودة البيانات (Data Quality Gate)

تُنفَّذ قبل كل تحليل، وتُخزّن في `data_quality_checks`:

| الفحص | القاعدة | أثره |
|---|---|---|
| الحداثة | آخر مزامنة لكل كيان أقل من حد الكيان (الحجوزات: ساعة، التكاليف: 30 يومًا) | تعطيل الكاشفات المعتمدة عليه، وإظهار السبب |
| اكتمال التكاليف | نسبة المبيعات التي لها تكلفة مباشرة معروفة | أقل من 80%: لا إعلان ربحية، و`margin_check = costs_incomplete` |
| الاتساق | مجموع البنود يساوي الإجمالي، والحالة متسقة مع المبالغ | تُستبعد السجلات المتناقضة، مع تعدادها |
| حجم العينة | الحد الأدنى لكل مقياس (معرّف في سجل المقاييس) | أقل منه: `insufficient_sample`، ولا رقم معروض |
| التكرار | مرشحو التكرار في العملاء والمعاملات | تحذير، مع تعداد تقديري |
| العملات والوحدات | عملة واحدة لكل منشأة، ووحدات المخزون متطابقة مع الوصفات | يمنع فحص المخزون عند عدم التطابق |
| تغير جوهري | قفزة أكبر من 3 انحرافات معيارية عن الأسابيع السابقة | وسم الفترة `regime_change`، وعدم مقارنتها بخط أساس قديم |

**مخرَج الفحص** تقرير بمستوى لكل مجال (`ok` / `limited` / `insufficient`) مع **ما الذي يحسّنه** (مثلًا: «سجّلي تكلفة 4 خدمات لتفعيل فحص الهامش»).

## 6. محركات النواة

### 6.1 تسلسل مهمة التحليل

```
gate(auth, scope, plan feature, budget)
  → snapshot(period, data_version)          # لقطة مثبتة بالمصدر والفترة وhash
  → quality_gate(snapshot)                  # §5.4
  → metrics(snapshot)                       # §6.4 بالكود
  → profile = load_profile(business)        # §8
  → candidates = detectors(metrics, profile, sector_pack)            # §6.5
  → for c in candidates: checks(capacity, inventory, margin, preferences, conflicts)  # §6.6–6.7
  → interventions = select_intervention(c, playbooks)                # §6.7
  → ranked = rank(candidates, weights)                                # §6.8
  → drafts = planner(ranked[:k], knowledge, timing) → validator      # §6.9–6.10 (AI أو قواعد)
  → persist(opportunities, evidence, plan_version) ; emit(plan.ready)
  → usage + audit
```

كل خطوة **حتمية وقابلة للإعادة** ما عدا المخطِّط. المخطِّط مُخزَّن في الكاش حسب `(business, prompt_version, snapshot_hash, candidates_hash, model)`.

### 6.2 اللقطة (Snapshot)

موجودة اليوم (`metric_snapshots`). تُوسَّع إلى:
- **`data_version`**: أعلى `source_version` لكل كيان. أي تغير ينتج لقطة جديدة، وغير ذلك تُعاد اللقطة السابقة (`reused`).
- **نطاقات زمنية صريحة**: فترة التحليل، وفترة المقارنة، وفترة التطلع (مثلًا: 90 يومًا للخلف للمعدلات و14 يومًا للأمام للطاقة).

### 6.3 سجل المقاييس (Metrics Registry)

كل مقياس يُعرَّف **مرة واحدة في الكود** ويُنعكس في `metric_definitions`:

```ts
defineMetric({
  key: 'offering.contribution_margin_unit', version: 2,
  label: { ar: 'هامش المساهمة للوحدة', en: 'Unit contribution margin' },
  unit: 'minor', grain: ['offering'], window: 'P90D',
  formula: 'net_price - (material_cost + commission + payment_fee + platform_fee)',
  requires: ['CostFact.material', 'CostFact.commission'], min_sample: 5,
  sectors: ['*'], compute: (ctx) => /* كود مُختبر */,
});
```

**مجموعة النسخة الأولى:**

| المجال | المقاييس |
|---|---|
| المبيعات | المبيعات المكتملة (صافي)، متوسط قيمة الطلب، المبيعات لكل خدمة أو منتج، مزيج القنوات |
| العملاء | العملاء النشطون، معدل التكرار، الدورة الوسيطة بين الزيارات لكل خدمة، المتأخرون عن دورتهم، مصادر الاكتساب |
| الجودة | الإلغاء من العميلة، عدم الحضور، متوسط التقييم وعدده، الشكاوى المؤكدة |
| الطاقة | الإشغال لكل مورد ويوم وساعة، الدقائق المتاحة في الأيام الـ 14 القادمة، الفترات الهادئة (أقل من 40%) والممتلئة (أكثر من 90%) |
| الطلب غير المخدوم | «لا مواعيد» لكل خدمة، قائمة الانتظار، بدء الحجز دون إتمام |
| الاقتصاديات | هامش المساهمة للوحدة والإجمالي، نسبة الخصم، العمولات، رسوم الدفع، عمولة السوق، اكتمال التكاليف |
| المخزون | المتاح، الاستهلاك الأسبوعي، أيام التغطية، الأصناف بطيئة الحركة (للبيع فقط) |
| التحويل | المشاهدة ← بدء الحجز ← تأكيد، والتحويل لكل مصدر |
| الحملات | المنسوب، والإضافي عند كفاية العينة، والتكلفة، وتكلفة الاكتساب |

**مصادر جديدة متاحة في luma3** (من المرحلة الثانية) تُضاف للموصل:
- عمولة الموظفة وفق سياسة العمولة (`commission_policies`)
- عمولة سوق لوما (`marketplace_commissions`)
- رسوم الدفع ومصدر العميلة (`acquisition_source`)
- طلبات التقييم، وحجوزات المناسبات، ونتائج الجرد (`stock_counts`)
- الإجازات المعتمدة كقيود طاقة

### 6.4 محرك الفرص (Opportunity Engine)

**كاشفات مسجّلة** بواجهة موحدة:

```ts
interface Detector {
  id: string;                         // 'quiet_capacity', 'lapsed_cohort', ...
  sectors: SectorId[];                // من الحزمة القطاعية
  requires: MetricKey[];              // المقاييس المطلوبة
  minQuality: Partial<Record<QualityDomain, 'ok' | 'limited'>>;
  detect(ctx: DetectContext): OpportunityCandidate[];   // حتمي، بلا AI
}
```

**كاشفات النسخة الأولى** (وما يقابلها حاليًا):

| الكاشف | الشرط (مختصر) | الموجود اليوم |
|---|---|---|
| `quiet_capacity` | فترات متكررة إشغالها أقل من 40% في الأيام الـ 14 القادمة، مع خدمات تناسب طولها | `quiet_periods` |
| `high_satisfaction_low_demand` | رضا أعلى من وسيط المنشأة، وطلب أقل من وسيطها، وطاقة متاحة | `service_promotion` جزئيًا |
| `lapsed_cohort` | عملاء تجاوزوا 1.5× دورة الخدمة الوسيطة، والعينة كافية | `reactivation` |
| `unserved_demand` | «لا مواعيد» أو انتظار مرتفع لخدمة | `pricing:demand` و`availability_empty` |
| `conversion_friction` | بدء حجز مرتفع مع تأكيد منخفض | `booking_experience` |
| `cross_sell_affinity` | منتج للبيع يشتريه عملاء خدمة معينة أكثر من المتوقع | **جديد** (لدينا أزواج خدمات فقط) |
| `slow_mover_bundle` | منتج **للبيع** بطيء الحركة، وباقة مع خدمة رائجة لها هامش موجب | **جديد** |
| `margin_leak` | خدمة هامشها منخفض أو سالب بعد العمولات والرسوم | `pricing:margin` |
| `missing_cost_blocker` | تكاليف ناقصة تمنع فحص فرص ذات أثر | `pricing:costs_missing` |
| `offering_presentation` | خدمة بمشاهدات وبلا صورة أو وصف، أو تحويل ضعيف | `content` |
| `loyalty_over_discount` | اعتماد متكرر على الخصم مع تكرار زيارة منخفض | `loyalty` |
| `capacity_prerequisite` | فرصة ذات أثر يمنعها قيد (وردية أو مواد) | **جديد**، ويُعرض كـ «متطلب قبل الحملة» |
| `seasonal_alignment` | حدث موثق **مرتبط** بفرصة داخلية قائمة | `seasonal` (يصبح مُلحقًا لا مستقلًا؛ P1) |
| `campaign_learning` | حملة انتهت بنتيجة قابلة للقراءة | `campaign_review` |

**دمج المكرر:** `fingerprint = detector + offering/segment + period_bucket`. الفرصة المفتوحة تُحدَّث أدلتها ولا تتكرر. الفرص المتشابهة تُجمع تحت فرصة أم واحدة.

### 6.5 دورة حياة الفرصة

| # | المرحلة | التنفيذ | الحقل الناتج |
|---|---|---|---|
| 1 | اكتشاف | كاشف | `detector_id`, `why_now` |
| 2 | جمع الأدلة والفترة | استعلامات المقاييس | `evidence[]`, `period` |
| 3 | فحص جودة البيانات | §5.4 | `data_quality` |
| 4 | الأسباب المحتملة | قواعد التشخيص (لا AI) | `hypotheses[]`، **موسومة كفرضيات** |
| 5 | الطاقة والمخزون | §6.6 | `capacity_check`, `inventory_check` |
| 6 | الجدوى المالية | §7 | `margin_check`, `scenarios[]` |
| 7 | الجمهور والسوق والتوقيت | الشرائح والرادار والتقويم | `target_segment`, `timing`, `market_context` |
| 8 | التدخل | منتقي التدخل والكتيبات | `recommended_action`, `alternatives_considered[]` |
| 9 | القياس | قوالب القياس | `success_metrics[]`, `measurement_design` |
| 10 | الترتيب والعرض | §6.8 | `priority`, `rank_explanation`, `review_at` |

الحالات: `detected → assessed → proposed → (studying | deferred | dismissed | accepted) → converted(plan_action | campaign_draft | price_proposal) → executed → measured → closed`. وأيضًا `superseded` / `expired` عند تغير الأسباب.

### 6.6 فاحص الطاقة والمخزون

لكل تدخل مقترح يُحسب **الحجم المستهدف** (عدد الخدمات الإضافية المطلوب). ثم:

1. **الوقت والموارد:** من `OfferingRequirement(type=time|resource|skill)` و`CapacityWindow`. عدد الخانات المتاحة فعلًا في نافذة الحملة، لموارد **مؤهلة** (المهارة)، مع غرفة أو جهاز عند اللزوم، بعد الإجازات المعتمدة والحجوزات.
   - النتيجة: `ok` (الخانات تكفي)، أو `constrained` (تكفي حتى N)، أو `blocked` (تحتاج وردية أو مورد)، أو `unknown` (لا جداول).
2. **المواد:** من `OfferingRequirement(type=material, confidence=recipe)` و`InventoryItem.on_hand`.
   - **إذا كانت الوصفة غير موجودة:** `inventory_check = unknown`، ورسالة صريحة «لا توجد وصفة استهلاك؛ لا يمكن تقدير عدد الخدمات الممكنة». **لا تقدير.**
   - **إذا كانت موجودة:** `covers_n = floor(min(on_hand_i / qty_i))`، مع `reorder_needed` إذا كان N المستهدف أكبر من `covers_n`.
3. **التعارض:** مبادرات معتمدة تستهلك نفس الموارد في نفس النافذة تُخصم أولًا.

النتيجة تُرفق بالبطاقة، وتُخفض الأولوية أو تحوّل الفرصة إلى `capacity_prerequisite` عند `blocked`.

### 6.7 منتقي التدخل

لكل كاشف قائمة تدخلات مرتبة في الحزمة القطاعية، ويُختار **أول تدخل يجتاز القيود**:

```
quiet_capacity:    [targeted_reminder, off_peak_package, value_add, content_feature, limited_discount]
lapsed_cohort:     [reminder_due, loyalty_reward, value_add, limited_discount]
unserved_demand:   [open_slots, waitlist_flow, staff_cross_training, price_review]
conversion_friction: [improve_description, simplify_booking, add_images, faq]
slow_mover_bundle: [bundle_with_top_service, gift_with_service]
```

- **تفضيلات المنشأة قيد صلب:** `no_discounts = true` يحذف كل `*_discount`. `max_discount_bp` يحدد السقف. الخدمات المستبعدة لا تُروَّج.
- **الخصم آخر خيار** دائمًا، ولا يُختار إلا إذا اجتاز فحص التعادل (§7) ووُجد مبرر من بيانات سابقة أو تجربة محدودة.
- يُحفظ `alternatives_considered[]` مع سبب الاستبعاد («الباقة: لا يوجد مكمّل بهامش موجب»).

### 6.8 الترتيب المفسَّر

```
score = Σ wᵢ · fᵢ   حيث كل fᵢ ∈ [0,1] بتعريف قاعدي منشور
```

| العامل fᵢ | التعريف (النسخة الأولى) | الوزن الافتراضي |
|---|---|---|
| توافق الهدف | 1 إذا خدم هدفًا معتمدًا ذا أولوية عليا، و0.5 لهدف ثانوي، و0 خلاف ذلك | 0.20 |
| قوة الدليل | `strong` 1 · `moderate` 0.66 · `limited` 0.33 · `insufficient` 0 | 0.20 |
| الأثر المحتمل | هامش المساهمة الإضافي في سيناريو متحفظ ÷ أعلى قيمة بين المرشحين | 0.20 |
| قابلية التنفيذ | `capacity ok` + `inventory ok` + لا متطلبات مسبقة | 0.15 |
| التكلفة والجهد | معكوس (التكلفة النقدية + ساعات العمل المقدرة) مطبَّع | 0.10 |
| التوقيت | نافذة مناسبة خلال 14 يومًا، أو حدث موثق مرتبط | 0.10 |
| المخاطر والتعارض | معكوس (تعارض موارد + أثر على الجودة + تجاوز التكرار) | 0.05 |

- **الأوزان قابلة للضبط** لكل منشأة (`ranking_weights` في الملف، ضمن حدود)، وكل بطاقة تعرض **أعلى عاملين** رفعاها وأدنى عامل خفّضها.
- **لا «درجة ثقة» رقمية.** قوة الدليل تُعرض كفئة لفظية مع أسبابها (حجم العينة، حداثة البيانات، اكتمال التكاليف).
- **حد العرض:** حتى 5 فرص نشطة في الصفحة الرئيسية. الباقي في «للدراسة». لا تنبيهات استعجال مصطنعة.

### 6.9 المخطِّط (LLM) وأدوات القراءة

- **المدخل** ليس اللقطة كاملة. يُعطى المخطِّط:
  - الفرص المرتبة (حتى k) مع أدلتها وفحوصها، كـ JSON بمعرّفات `ev_*`;
  - ملخص الملف (الأهداف، النبرة، القيود);
  - مقتطفات معرفة مسترجعة (§9);
  - الأحداث الموثقة ذات الصلة.
- **أدوات قراءة مقيّدة اختيارية** عند الحاجة لتفصيل، مثل `get_metric(key, grain_ref)` و`get_segment_size(segment_def)` و`get_capacity(window, offering_ref)`. كلها مقيدة بالمنشأة بالكود، وبلا SQL مفتوح، وبعدد استدعاءات محدود.
- **المخرَج** JSON Schema صارم (§11.1). النموذج **لا يضيف أرقامًا** إلا بمرجع `evidence_ref` أو وسم `assumption`.
- **اختيار النموذج حسب المهمة:** صياغة البطاقات والمحتوى الأولي بنموذج متوسط، وتجميع الخطة الشهرية بنموذج أقوى. الإعداد في `prompt_versions.model_tier`.
- **عند عدم توفر AI:** المخطِّط بالقواعد الحالي (`rules.ts`) يُنتج نفس البنية بنص قالبي، مع ملاحظة «خطة بالقواعد».

### 6.10 المدقِّق (Validator)

يمتد من `validate.ts` الحالي، **ويرفض أو يعلّم** قبل الحفظ:

| الفحص | الفشل |
|---|---|
| كل رقم في النص له `evidence_ref` يطابق القيمة، أو موسوم `assumption` | رفض البند (وإعادة صياغة مرة واحدة) |
| مجموع الميزانية أقل من أو يساوي ميزانية المنشأة للفترة | رفض الخطة، أو تقليص بالقواعد |
| `capacity_check` و`inventory_check` و`margin_check` موجودة وغير متناقضة مع الحسابات | رفض |
| احترام التفضيلات (لا خصم، سقف الخصم، الخدمات المستبعدة، النبرة) | رفض |
| لا ادعاءات علاجية أو صحية غير مثبتة (قائمة أنماط عربية وإنجليزية + حزمة القطاع) | رفض البند |
| لا ترويج لخانات ممتلئة | رفض |
| تواريخ المناسبات من مصدر موثق فقط | حذف الحدث |
| `review_at` موجود ومنطقي | إضافة افتراضي (14 يومًا) |

## 7. الجدوى الاقتصادية: الهامش والتعادل والسيناريوهات

### 7.1 تعريفات

- **هامش المساهمة للوحدة** `m = p − v`، حيث `v` = مواد + عمولة الموظفة + رسوم الدفع + عمولة المنصة (إن كان الحجز من السوق) + تكلفة متغيرة أخرى.
- عند **اكتمال تكاليف أقل من 80%** للخدمة: `margin_check = costs_incomplete`، ولا تُحسب الصيغ أدناه بأرقام مطلقة. تُعرض كنسب مشروطة: «إذا كانت التكلفة المتغيرة X…».

### 7.2 تعويض الخصم (الصيغة المعتمدة)

```
m₀ = p − v                 # الهامش قبل
m₁ = p·(1−d) − v           # الهامش بعد خصم d
N₀ = الحجم الأساسي المتوقع في الفترة (من خط الأساس)
C  = تكلفة الحملة الثابتة

الحجم المطلوب للتعادل:  N₁ = (N₀·m₀ + C) / m₁
الزيادة المطلوبة:       Δ% = N₁/N₀ − 1
```

**المثال المرجعي (اختبار وحدة إلزامي):** p=200، v=80، d=15%. إذن m₀=120 وm₁=90، ومع C=0 تكون Δ = 120/90 − 1 = **33.3%**.

ثم يُعرض بوضوح:

| السؤال | المصدر | الحالة إذا لم يتوفر |
|---|---|---|
| هل الطاقة تستوعب N₁؟ | §6.6 | `unknown`، والفرصة لا تتجاوز «دراسة» |
| هل توجد أدلة استجابة؟ | حملات سابقة مماثلة بنتيجة **إضافية** | «لا توجد أدلة استجابة؛ نقترح تجربة محدودة» |
| كم من الخصم سيذهب لمن كان سيشتري أصلًا؟ | نسبة العملاء المستهدفين الذين اشتروا بالسعر الكامل في الفترة المقابلة | يُعرض كخطر، مع اقتراح استهداف المتأخرين فقط |
| بديل أفضل؟ | منتقي التدخل | تُعرض البدائل وهامشها |

**إذا كان m₁ ≤ 0:** يُرفض الخصم آليًا.

### 7.3 رفع السعر

لا يُفترض ثبات الطلب. تُعرض سيناريوهات مرونة (−0.5 و−1 و−1.5) بنقطة التعادل `ΔN_breakeven = 1 − m₀/m₁'`، مع تجربة مقترحة (فرع واحد، أو خدمة جديدة بنفس المكونات، أو فترة محددة). **لا تنفيذ تلقائي**، والتحويل لـ «مقترح سعر» بنقرة، واعتماد في الكتالوج كما هو اليوم.

## 8. ملف معرفة المنشأة (Business Profile)

### 8.1 البنية

كل معلومة **حقيقة (fact)** بمصدر ودرجة وتاريخ:

```ts
type ProfileFact = {
  key: string;                       // 'goal.primary', 'audience.core', 'pref.no_discounts', 'offering.grow:<id>'
  value: Json;
  kind: 'computed' | 'explicit' | 'inferred';   // محسوب / صريح من المستخدم / مستنتج قابل للتصحيح
  source: { type: 'metric' | 'user' | 'connector' | 'model'; ref: string };
  confidence?: 'high' | 'medium' | 'low';       // للمستنتج فقط، بلا أرقام
  valid_from: string; updated_at: string; updated_by?: string;
  superseded_by?: string;
};
```

### 8.2 المحتوى

| القسم | أمثلة | المصدر الافتراضي |
|---|---|---|
| الهوية | القطاع والمدينة والفروع ونطاق الخدمة | `connector` (محسوب) |
| الأهداف والأولويات | «زيادة الحجوزات في الأيام الهادئة»، «تنمية خدمات العناية» | `user` (صريح) |
| الجمهور | الشرائح الرئيسية والفئة العمرية إن وُجدت | `inferred` (من البيانات) + تصحيح المستخدم |
| النبرة والهوية | رسمي أو ودود، كلمات محظورة | `user` |
| الميزانية | شهري، ولكل قناة | `user` |
| حدود الخصم | `no_discounts` و`max_discount_bp` | `user` (موجود اليوم في `marketing_preferences`) |
| تنمية / استبعاد | خدمات للتنمية وخدمات لا تُروَّج | `user` |
| الموارد والقيود | الطاقة وقيود التوظيف والمخزون | `computed` |
| ذاكرة القرار | أسباب القبول والرفض المصنّفة | `user` عبر القرارات (§10) |

**الاستنتاج لا يطغى على الصريح:** عند التعارض تُعرض الحقيقة الصريحة، ويُعلّم المستنتج بـ «يحتاج مراجعة».

## 10. الذاكرة والقياس والتعلم

### 10.1 سلّم القرار والتنفيذ (مسار منفصل لكل مرحلة)

| المرحلة | الحدث | ملاحظات |
|---|---|---|
| `viewed` | فُتحت البطاقة | للاستخدام فقط، ليس إشارة جودة |
| `reacted` | إعجاب أو عدم إعجاب | ذوق، **لا يُستخدم كنتيجة** |
| `decided` | اعتماد / تعديل+اعتماد / تأجيل / رفض | **مع سبب مصنّف إلزامي للرفض والتأجيل** |
| `scheduled` | تحويل لخطة أو حملة أو مقترح سعر | |
| `executed` | تنفيذ فعلي بتاريخ (من الموصل أو يدويًا) | |
| `completed` | انتهاء النافذة | |
| `measured` | النتيجة مع جودة القياس | |

**تصنيف أسباب الرفض** (يمنع الاستنتاج الخاطئ): `capacity_staffing`، `capacity_inventory`، `budget`، `brand_fit`، `timing`، `already_doing`، `disagree_with_data`، `not_valuable`، `other(text)`.
- الرفض بسبب `capacity_*` أو `budget` أو `timing` **لا يُحتسب** فشلًا للفكرة التسويقية.
- `brand_fit` يُحدّث تفضيلًا مستنتجًا يحتاج تأكيد المستخدم.

### 10.2 سجل المبادرة (Initiative Record)

```
baseline (قبل)            → مقاييس الفترة المقابلة، اللقطة، data_version
original_proposal          → نسخة مجمّدة من البطاقة
user_edits                 → diff
approved_version
execution                  → ما نُفذ فعلًا، التوقيت، الجمهور، القناة، التكلفة الفعلية
results                    → المقاييس الأساسية والثانوية وحواجز الأمان (إلغاءات، جودة، إشغال زائد)
external_factors           → أحداث متزامنة (موسم، نفاد مخزون، تغيير سعر آخر)
measurement_quality        → 'experimental' | 'quasi' | 'observational' | 'insufficient'
```

### 10.3 القياس

- **الإضافي مقابل المنسوب:** موجود للحملات (holdout + حد 30). يُعمَّم على كل مبادرة قابلة للتجزئة.
- **عند عدم إمكانية التجزئة** (تحسين وصف، فتح مواعيد): مقارنة بفترات مماثلة وخدمات ضابطة، وتُعرض كـ `observational` و**إشارة محدودة لا علاقة سببية**.
- **مقاييس حسب الهدف:** الحجوزات المكتملة، هامش المساهمة، تكلفة الاكتساب، التكرار، الاستعادة، استغلال الهادئ، البيع المكمل، مع **حواجز أمان** للإلغاءات والاستردادات وأثر الإشغال على التقييم.

### 10.4 طبقات التطور الثلاث

| الطبقة | ماذا يتحسن | متى | كيف |
|---|---|---|---|
| 1. ذاكرة المنشأة | السياق: الأهداف والتفضيلات والقيود والقرارات | من اليوم الأول | حقائق الملف + سجل القرار، **بلا تدريب أوزان** |
| 2. نماذج متعلّمة | توقع الطلب لكل خدمة واليوم والساعة، واحتمال العودة، والاستجابة لنوع التدخل، وترتيب الفرص | عند حدود بيانات معلنة (مثلًا: 180 يومًا و500 معاملة مكتملة للمنشأة، أو بيانات مجمعة **بموافقة** لنماذج القطاع) | خط أساس أولًا (موسمي ساذج، ومتوسطات)، ثم GBM أو نماذج زمنية، والتعلم العميق فقط إن تفوّق على الخط الأساسي |
| 3. اختيار بالتجارب | اختيار القناة أو صيغة الرسالة أو التوقيت | بعد الطبقة 2، وضمن تجارب **معتمدة** | Contextual Bandits بحدود استكشاف. **ممنوع على الأسعار** وعلى الإرسال بلا اعتماد |

### 10.5 حوكمة النماذج

- `model_versions`: الإصدار، والبيانات (نطاق زمني + hash)، والمقاييس، والحالة (`candidate` / `shadow` / `active` / `retired`).
- **تقسيم زمني صارم:** تدريب حتى T، واختبار بعد T. لا خلط عشوائي.
- **بوابة ترقية:** يتفوق على الإصدار النشط **وعلى** الخط الأساسي بفارق معلن في مقياس معلن، بلا تراجع في حواجز الأمان. ثم فترة **ظل (shadow)**، ثم تفعيل. الرجوع بنقرة.
- **عدم التدريب المشترك** على بيانات منشأة دون موافقة صريحة مسجلة. نماذج القطاع تُدرَّب على مجاميع مستعارة الهوية من منشآت موافقة فقط.

## 12. الرادار والتوقيت والسوق

### 12.1 الإشارات

يمتد من `trend_sources` و`trend_observations` الحاليين:

| الحقل | ملاحظة |
|---|---|
| `source`, `url`, `published_at`, `observed_at`, `region`, `topic` | إلزامية |
| `reach_metrics` | فقط ما يقدّمه المصدر فعلًا، و`null` غير ذلك |
| `evidence_class` | `example` (مثال متكرر) / `early_signal` / `supported_trend` (بأرقام من المصدر) |
| `freshness` / `valid_until` | تحدد الصلاحية |
| `cluster_id` | تجميع الإشارات المتعلقة بنفس الموضوع |

**مصادر إضافية (المرحلة 4):**
- APIs للبحث والاهتمام (إن توفرت بترخيص).
- تقويمات رسمية للمناسبات الوطنية والإجازات الدراسية.
- روابط يضيفها المستخدم.

كلها عبر `safe-fetch` الحالي، ومحتواها **غير موثوق** (`untrusted_*`).

### 12.2 الصلة والملاءمة

تقييم الصلة **بالقواعد أولًا**: تطابق القطاع والجمهور والمنطقة، وارتباطه بفرصة داخلية مفتوحة (P1). ثم صياغة «كيف نطبّقها» بالنموذج.

**المناسبات الصحية:** الحزمة القطاعية تحدد أن المحتوى `awareness_only`. المدقِّق يرفض أي ادعاء علاجي، ويمنع ربط المناسبة بخصم مباشر إلا بنص توعوي منفصل.

### 12.3 السوق والمنافسون

- **ملاحظات سوقية** في `market_observations`:
  - النوع: `competitor_offer` / `price_point` / `audience_need` / `channel_norm`.
  - المصدر والتاريخ والمنطقة وقابلية المقارنة: `comparable` / `partial` / `not_comparable`، مع أسبابها (اختلاف المدة أو المكونات أو الجودة).
- **قاعدة صلبة:** سعر منافس **لا يكفي وحده** لاقتراح تغيير سعر. يُستخدم كسياق مع الهامش والطلب والجودة، ويُعرض «غير قابل للمقارنة» عند اختلاف الخدمة.

## 13. الجدولة وإعادة التحليل

- **الطابور:** `ai_jobs` الحالي بحالاته (`queued`/`running`/`succeeded`/`failed`/`insufficient_data`/`unavailable`)، ومحاولات محدودة، ووحدانية `(tenant, kind, period_key)`. يُعمَّم لأنواع جديدة: `sync`، `quality`، `detect`، `measure`، `train`.
- **مُجمّع التغيرات (Change Aggregator):** أحداث الموصل تُحوَّل إلى إشارات تغير في `change_signals` بمفتاح `(business, type, scope)`. قاعدة **عتبة + نافذة تهدئة** (مثلًا 30 دقيقة) تقرر متى نعيد تحليل فرص محددة فقط:

| الإشارة | العتبة | ما يُعاد |
|---|---|---|
| مادة تحت حد إعادة الطلب أو نفاد | أي صنف في وصفة خدمة مُروَّج لها | فحص المخزون للفرص والخطط المتأثرة |
| امتلاء نافذة | إشغال أكبر من 90% في نافذة مبادرة | فحص الطاقة، وتجميد الترويج فيها |
| غياب أو إجازة معتمدة | تقلص الطاقة أكثر من 20% في نافذة | فحص الطاقة |
| تغير تكلفة أو سعر | تغير الهامش أكثر من 10% | فحص الهامش |
| نتيجة حملة | اكتمال القياس | التعلم + `campaign_learning` |

- **لا استدعاء للنموذج** في إعادة الفحص. النموذج يُستدعى فقط إذا تغيرت **قائمة الفرص المختارة** أو طلب المستخدم إعادة صياغة.
- **الخطة المعتمدة لا تتغير بصمت:** النتيجة مقترح تعديل (إصدار) مع سببه.
- **فشل التوليد** لا يمس الخطة السابقة (كما اليوم).

## 15. واجهات Loom API v1

كل عملية تفرض **المصادقة + نطاق المنشأة + الصلاحية + zod + حدود الاستخدام + Idempotency-Key** للعمليات المنشئة.

| المجموعة | المسار (مقترح) | الصلاحية |
|---|---|---|
| الربط | `POST /loom/v1/businesses/{b}/connections` · `GET …/connections/{c}` (الحالة، آخر مزامنة، الأخطاء) · `POST …/connections/{c}/sync` | `loom.connections.manage` |
| الأحداث | `POST /loom/v1/ingest/{connection}` (webhook موقّع HMAC، idempotent بمعرّف الحدث) | توقيع الموصل |
| الجودة | `GET …/data-quality` | `loom.view` |
| الملف | `GET/PATCH …/profile` · `PUT …/goals` · `PUT …/preferences` | `loom.manage` |
| التحليل | `POST …/analyses` (kind, period) ← `202 {job_id}` · `GET …/jobs/{id}` | `loom.manage` |
| الفرص | `GET …/opportunities?status=&category=` · `GET …/opportunities/{id}` · `POST …/opportunities/{id}/decision` (approve, defer, dismiss+reason, edit) · `POST …/opportunities/{id}/convert` (plan_action, campaign_draft, price_proposal) | القراءة `loom.view`، والقرار `loom.manage`، والتحويل لحملة أو سعر عبر صلاحية النظام المضيف |
| الخطط | `GET …/plans` · `GET …/plans/{id}/versions` · `POST …/plans/{id}/transition` | `loom.view` / `loom.manage` |
| التنفيذ والنتائج | `POST …/initiatives/{id}/executions` · `GET …/initiatives/{id}/outcome` | `loom.manage` |
| السجل | `GET …/decisions` · `GET …/plans/{id}/diff` | `loom.view` |

**Webhooks صادرة للنظام المتصل:** `plan.ready`، و`opportunity.created`، و`plan.revision_proposed`، و`outcome.measured`. **اعتماد الخطة لا يرسل حملة.** الإرسال أمر منفصل عبر `ActionPort` في النظام المضيف، بموافقاته (في لوما: `campaigns.approve` والرضا والحظر والتكرار).

**في لوما:** صلاحيات `loom.*` تُربط بالحالية: `marketing.view` إلى `loom.view`، و`marketing.manage` إلى `loom.manage`، و`business.manage` إلى `loom.connections.manage`.

## 16. الحزم القطاعية (Sector Packs)

```ts
interface SectorPack {
  id: 'beauty' | 'retail' | 'restaurant' | 'professional_services' | string;
  version: string;
  vocabulary: Record<CanonicalTerm, { ar: string; en: string }>;  // «أخصائية» مقابل «موظف» مقابل «طاهٍ»
  capacityModel: { resources: ResourceKind[]; unit: 'minutes' | 'covers' | 'orders' | 'hours'; peakDefinition: … };
  metrics: { enable: MetricKey[]; overrides: Partial<Record<MetricKey, MetricOverride>> };
  detectors: Array<{ id: string; params: Record<string, number> }>;
  interventions: Record<DetectorId, InterventionKind[]>;
  validation: { forbiddenClaims: RegExp[]; awarenessOnlyTopics: string[] };
  campaignTemplates: TemplateRef[];
}
```

| القطاع | الطاقة تعني | قيود خاصة |
|---|---|---|
| تجميل (الأول) | دقائق الأخصائيات المؤهلات + الغرف والأجهزة | مواد التشغيل لكل خدمة، الادعاءات الصحية |
| متجر | المخزون + تجهيز الطلبات + قدرة التسليم | دوران المخزون، الإرجاع |
| مطعم | التحضير + الطاولات + المكونات + الذروة | صلاحية المكونات، أوقات الخدمة |
| خدمات مهنية | ساعات الفريق + المهارات + التزامات المشاريع | الحجز المسبق الطويل |

**قاعدة:** أي نظام جديد **لا يعمل بمجرد التوصيل**. يجب تعبئة `source_mappings` (ما معنى «خدمة» و«إيراد» و«مكتمل»)، ثم تمرير فحص الجودة، ثم مراجعة بشرية لأول لقطة.

## 17. الخصوصية والأمان

| الضابط | التطبيق |
|---|---|
| العزل | RLS على كل جداول `loom` بـ `business_id`. الكاش مفتاحه يشمل المنشأة (موجود ومُختبر). |
| تقليل البيانات للنموذج | مجاميع ومعرّفات مستعارة (`S1`، `seg_3`). لا أسماء ولا أرقام. `input_summary` في `ai_runs` بلا بيانات شخصية (موجود). |
| عدم التدريب المشترك | علم `shared_training_consent` لكل منشأة، افتراضيه `false`. |
| الأسرار | على الخادم فقط (موجود). |
| المحتوى الخارجي | `untrusted_*` + `safe-fetch` ضد SSRF (موجود). |
| صلاحيات النموذج | أدوات قراءة محددة بالمنشأة بالكود، وحد استدعاءات، وبلا SQL، وبلا كتابة. |
| فصل الأدوار | الدراسة (`loom.view`) والاعتماد (`loom.manage`) والتنفيذ (صلاحيات النظام المضيف: `campaigns.approve`، `catalog.edit`). |
| التدقيق | القرارات وتعديلات الملف والأوزان والتحويلات تُسجَّل في `audit_logs`. |
| الحملات | الرضا، وإلغاء الاشتراك، والحظر، والتكرار، وساعات الهدوء (موجود). |

## 18. التكلفة والأداء

- الأرقام بالكود، والنموذج للصياغة فقط.
- إعادة استخدام اللقطة عند تطابق `data_version` (موجود: `reused`).
- كاش المخطِّط بمفتاح يشمل `candidates_hash`: لا إعادة توليد لنفس الفرص.
- اختيار النموذج حسب المهمة (`model_tier`).
- ميزانية شهرية ذرية لكل منشأة (موجود: `limit.ai_runs_monthly`) + سقف تكلفة يومي على مستوى المنصة.
- تسجيل التكلفة الفعلية عند توفر التسعير (موجود).
- **تعطل مزود AI لا يوقف شيئًا:** القواعد تكمل، والخطط السابقة باقية، ووظائف لوما التشغيلية مستقلة تمامًا.

## 19. مراحل التنفيذ (مربوطة بالكود الحالي)

| المرحلة | النطاق | المخرجات القابلة للتجربة | معيار القبول |
|---|---|---|---|
| **1. العقود والحدود** | `src/loom/` + مخطط `loom`. النموذج القانوني وموصل لوما (دروس `loom_export.*`). سجل المقاييس v1. فحص الجودة. الأهداف والتفضيلات في الملف. نقل `buildSnapshot` ليعمل فوق الموصل. | لقطة من الموصل تطابق اللقطة الحالية على بيانات البذور | اختبار تطابق + اختبار معماري يمنع الاستيراد من `domains/*` + RLS |
| **2. الفرص المفسَّرة** | الكاشفات (الحالية + `cross_sell_affinity` + `slow_mover_bundle` + `capacity_prerequisite`). فاحص الطاقة والمخزون. حاسبة الهامش والتعادل. منتقي التدخل مع التفضيلات. الترتيب بأوزان. جدول الأدلة. | بطاقات فرص كاملة الحقول **بالقواعد** | الاختبارات الإلزامية في §20 |
| **3. الصياغة والخطط** | المخطِّط بأدوات القراءة. المدقِّق الموسع. `plan_actions` كجداول. الصفحة الرئيسية الجديدة وبطاقة الفرصة. | خطط شهرية وأسبوعية بالنموذج **أو** القواعد بنفس العقد | 0 أرقام غير مسنودة في 100 تشغيل على بيانات البذور |
| **4. السوق والتوقيت** | مصادر API والتقويمات الرسمية، وتجميع الإشارات، وتقييم الصلة، والملاحظات السوقية. التوعوي مقابل الترويجي. | رادار بإشارات مصنفة ومرتبطة بفرص داخلية | لا فرصة موسمية بلا فرصة داخلية |
| **5. الذاكرة والقياس** | سلّم القرار وأسباب الرفض. سجل المبادرة. القياس العام (holdout، قبل/بعد مع ضابط). مُجمّع التغيرات وإعادة الفحص. | صفحة نتائج + مقترحات تعديل تلقائية للخطط | حالات «تغير البيانات بعد اعتماد خطة» |
| **6. النماذج المتعلّمة** | خطوط أساس، ثم توقع الطلب والعودة. سجل النماذج. الظل والترقية والرجوع. | توقعات موسومة `model_forecast` بجانب الأهداف | تفوّق موثق على الخط الأساسي بتقسيم زمني |
| **7. التوسع** | موصل CSV/REST عام، وحزمة قطاعية ثانية، واستخراج الخدمة إن لزم. | منشأة غير لوما تحصل على فرص بعد الربط والمراجعة | نفس اختبارات القبول بحزمة القطاع الجديد |

كل مرحلة تُعلِن في الواجهة ما هو **تجريبي**، وفي `IMPLEMENTATION_STATUS.md` ما يعمل فعلًا.

## 20. معايير قبول النسخة الأولى والاختبارات الإلزامية

النسخة الأولى (المراحل 1–3 + أساس 5) ناجحة إذا تحققت كلها. كل بند اختبار تكامل على بيانات بذور منظمة:

| # | الحالة | السلوك المتوقع |
|---|---|---|
| T1 | تكاليف ناقصة (أقل من 80%) لخدمة | `margin_check = costs_incomplete`، ولا ربحية مطلقة، وفرصة `missing_cost_blocker` |
| T2 | مخزون غير كافٍ ووصفة موجودة | `inventory_check = reorder_needed`، و`covers_n` صحيح، ومتطلب «إعادة طلب» |
| T3 | لا وصفة استهلاك | `inventory_check = no_recipe`، **ولا عدد مختلق** |
| T4 | مواعيد ممتلئة في نافذة | لا ترويج لها، و`capacity_check = blocked` أو `constrained`، ومقترح `unserved_demand` بدلًا منه |
| T5 | خصم 15% على 200 بتكلفة 80 | `breakeven_volume_increase = 0.333` (±0.001) |
| T6 | `no_discounts = true` | لا تدخل من نوع `*_discount` في أي فرصة أو خطة |
| T7 | مصدر ترند قديم (أكثر من 45 يومًا) | لا يصبح إشارة حية، ويُعرض كقديم |
| T8 | حدث موسمي بلا فرصة داخلية | لا فرصة موسمية مستقلة |
| T9 | AI غير متوفر | خطة بالقواعد بنفس العقد مع ملاحظة صريحة، والخطط السابقة سليمة |
| T10 | تغير البيانات بعد اعتماد خطة (نفاد مادة) | الخطة المعتمدة لا تتغير، ومقترح تعديل بإصدار جديد وسببه |
| T11 | منشأة جديدة (أقل من 30 يومًا، وأقل من 20 معاملة) | خطة استكشافية وتجارب محدودة، وقائمة «البيانات المطلوبة»، بلا تقسيمات دقيقة |
| T12 | عزل | لا تسرب فرص أو لقطات أو كاش أو معرفة بين منشأتين |
| T13 | رفض بسبب `capacity_staffing` | لا يُحتسب فشلًا للفكرة، ويُعاد العرض عند توفر الطاقة |
| T14 | رقم في مخرج النموذج بلا مرجع | يُرفض البند أو يُوسم «افتراض» |
| T15 | سعر منافس أقل | لا مقترح خفض سعر بناءً عليه وحده |

## 21. القرارات المفتوحة (تحتاج اعتمادًا قبل المرحلة 2)

1. **الأوزان الافتراضية للترتيب** (§6.8): هل تُعتمد كما هي أم تُعدَّل بعد مراجعة 20 منشأة تجريبية؟
2. **حد اكتمال التكاليف** لإعلان الهامش (80% مقترح).
3. **حدود البيانات** لتفعيل النماذج المتعلّمة لكل منشأة (180 يومًا و500 معاملة مقترح)، وهل نطلب موافقة صريحة على التدريب المجمّع على مستوى القطاع.
4. **مصادر المناسبات الرسمية** المعتمدة للسعودية (والترخيص).
5. **أول قطاع خارج لوما** (متجر أم مطعم) لتصميم الحزمة الثانية.
